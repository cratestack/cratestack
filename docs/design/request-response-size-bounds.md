# Design proposal for #413 — request/response size bounds (revised)

> **Status: implemented.** The maintainer settled the three decisions below (see "Decisions made (final)"); the implementation matches Decision 1's Option A, Decision 2's Option D, and Decision 3's Option B, with one numeric departure from this doc's own recommendation — see that section for the exact values and why.

This is a design note, not a PR. It exists to make the three judgement calls the maintainer needs to make before #413 is implementable; no code changes are proposed here.

## Decisions made (final)

1. **Frame cap (Decision 1): Option A**, as recommended — `/rpc/batch` rejects any batch over `BATCH_MAX_ITEMS` (1000 frames) before dispatching a single frame, via a length check in `build_batch_block()` (`crates/cratestack-macros/src/include/server/rpc_module/batch.rs`), erroring `CoolError::Validation("batch size {len} exceeds maximum of {BATCH_MAX_ITEMS}")` — the exact message shape `cratestack-sqlx`'s and `cratestack-rusqlite`'s own `validate_batch_size` already use.
2. **Request body limit (Decision 2): Option D's mechanism (a real constructor parameter), but a different default than this doc recommended.** `router()` and `rpc_router()` both take an explicit `body_limit_bytes: usize`, applied once via `.layer(axum::extract::DefaultBodyLimit::max(body_limit_bytes))` — exactly Option D's shape, and the override this doc's Decision 2 spent most of its length proving actually works this way (a value threaded through the function call, not re-layered after the fact). **The default is `DEFAULT_BODY_LIMIT_BYTES = 1 MiB` (`crates/cratestack-core/src/limits.rs`), not the `2 MiB` this doc's Decision 2 argued for.** The maintainer chose a real, considered ceiling for this framework's typical payload shapes over matching axum's built-in `Bytes` default or `MAX_BODY_BYTES` (the idempotency middleware's own 2 MiB buffering cap) — deliberately *not* rounded up to either. `BATCH_MAX_ITEMS` (1000 frames) still fits comfortably inside a 1 MiB request at any realistic average frame size, so this doc's "supporting number check" still holds at the new value.
3. **Response-rebuffer bound (Decision 3): Option B**, as recommended — `MAX_RESPONSE_REBUFFER_BYTES = 4 * DEFAULT_BODY_LIMIT_BYTES` (4 MiB at the current default), used at all four `to_bytes(usize::MAX)` sites (`crates/cratestack-axum/src/rpc/{batch,error_encode,grpc_bridge,codec_helpers}.rs`). The 4× multiplier and its `MAX_LIST_LIMIT`/`BATCH_MAX_ITEMS` grounding are unchanged from the recommendation below; only the base number moved with Decision 2.

**Coherence note the maintainer asked to have flagged explicitly:** with `DEFAULT_BODY_LIMIT_BYTES` now *tighter* than `MAX_BODY_BYTES` (1 MiB vs. the idempotency middleware's 2 MiB buffering cap), `MAX_BODY_BYTES` is — by the numbers alone — the *looser* of the two. Traced through the actual mechanism (`crates/cratestack-axum/src/idempotency/service.rs`), this doesn't reopen the request-body vector `DefaultBodyLimit` closes: `IdempotencyService` is a consumer-applied `tower::Layer` that wraps *around* the router cratestack returns, so it runs before the router's own `DefaultBodyLimit`-layered handlers; it buffers the raw request body itself via a direct `axum::body::to_bytes(body, MAX_BODY_BYTES)` call (not through the `DefaultBodyLimit` extension at all), succeeds for anything under its own 2 MiB, and reconstructs a new, fully-buffered request to hand to the router. That reconstructed request then reaches the router's inner `Bytes` extractor, which re-checks the (already fully in-memory) body against the router's own 1 MiB `DefaultBodyLimit` extension and rejects it there if it's over — `axum-core`'s `Limited` body wrapper enforces the cap per read, regardless of whether the underlying body is streamed or already fully materialized. Net effect at the default (1 MiB router limit, 2 MiB idempotency buffer): a body between 1 MiB and 2 MiB is accepted by `IdempotencyService`'s own buffering step but still rejected by the router's tighter limit one layer in — `MAX_BODY_BYTES` is effectively dead weight on that path today, not a bypass. It becomes live again only for a consumer who raises `body_limit_bytes` above 2 MiB without separately reconsidering `MAX_BODY_BYTES` — at that point the idempotency buffer, not the router, becomes the binding request-size ceiling for idempotent routes specifically. Retuning `MAX_BODY_BYTES` itself was out of scope here and not requested; this PR leaves it unchanged and flags the interaction rather than silently changing it.

## Decisions needed (up front)

1. **`/rpc/batch` frame cap** — hardcode a reuse of `BATCH_MAX_ITEMS`, or give batch-over-RPC its own distinct, tunable knob?
2. **Request body limit default + override mechanism** — what number, and how does a consumer change it (env var / builder param / re-layering)?
3. **Response-rebuffer bound** (the four `to_bytes(usize::MAX)` sites) — same number as (2), or a separate, larger constant?

## One correction to the issue's framing, load-bearing for (2)

The issue states "no matches for `DefaultBodyLimit`/`RequestBodyLimitLayer`" and frames this as *zero* request-body limit. That grep is accurate but the conclusion isn't quite right: every generated handler extracts `axum::body::Bytes` (confirmed at `crates/cratestack-macros/src/include/server/rpc_module/batch.rs:15`, `rpc_module.rs:96,137`, `axum_module.rs:52`), and axum's own `Bytes: FromRequest` impl refuses bodies over **2 MiB by default**, with no layer required — verified directly against the vendored `axum-core-0.5.6` source (`extract/default_body_limit.rs`'s own doc comment: "For security reasons, `Bytes` will, by default, not accept bodies larger than 2MB"), which is what `Cargo.lock` actually pins (`axum 0.8.9` / `axum-core 0.5.6`). So request bodies are *already* implicitly capped at 2 MiB today; the gap is that this default is invisible, undocumented, and not expressed anywhere in cratestack's own code or docs.

The other two defects are not softened by this: the `/rpc/batch` frame count has no cap regardless of body size (a 2 MiB body can hold thousands of minimal frames, each running a full `authenticate()` + policy + dispatch — confirmed: `rpc_dispatch_inner`, which every batch frame re-enters via `rpc_batch_dispatch`'s loop in `batch.rs:61-66`, is the exact same dispatcher unary calls, arm bodies included), and the four `to_bytes(usize::MAX)` response-rebuffer sites are outside `DefaultBodyLimit`'s reach entirely — it only ever governs inbound request bodies, never what a handler's own `Response` buffers back out.

## Prior art (this repo has strong opinions — three established patterns, not two)

**Pattern A — hardcoded structural constant, same for every deployment, no override.** `cratestack-core::MAX_LIST_LIMIT` (`crates/cratestack-core/src/page.rs:20`, `pub const MAX_LIST_LIMIT: i64 = 1000`) and `cratestack-core::BATCH_MAX_ITEMS` (`crates/cratestack-core/src/batch.rs:146`) are both this shape — **note these are in two separate files, not co-located**, each owned by the module whose concern it bounds (page.rs owns paging, batch.rs owns batch), which matters for where any new constant should live (see Reviewer notes). `BATCH_MAX_ITEMS`'s own doc comment warns against per-op deviation ("deviating per-op would invite footguns where `batch_get` accepts a list that `batch_create` of the same length rejects"). Enforcement is duplicated per-backend on purpose — `crates/cratestack-sqlx/src/query/batch/validate.rs:11` and `crates/cratestack-rusqlite/src/batch/support.rs:14` each have their own `validate_batch_size` returning a backend-native error type, sharing only the constant. `crates/cratestack-pg/tests/list_limit_cap.rs` is the regression test for this pattern's introduction (#123) and is the template for testing a numeric ceiling against the real generated route via `tower::util::ServiceExt` — **this specific test is itself PG-backed** (`pg::connect_or_skip()`), useful as a style template but not as evidence that testing a numeric cap requires no DB; that depends on which schema/route is under test (see Decision 1's test plan).

**Pattern B — imperative, deployment-tuned config, layered onto the `Router` after generation, never baked into a `.cstack` schema attribute or a compiled Rust `pub const`.** This is a *decided* precedent: `docs/design/idempotency-rate-limit-declarative-surface.md` §4.1 rejects putting rate-limit numbers into `.cstack` schema attributes, reasoning that "`.cstack` compiles to Rust consts" so retuning a limit during an incident would mean recompile + redeploy — "a strictly worse operational story for a control that exists specifically for incident response." **This reasoning is not scoped to schema attributes only** — it applies word-for-word to a `pub const` in `cratestack-core` too: changing that value also requires bumping and republishing `cratestack-core` (this workspace's lockstep version, per `just bump`/`just release` in `CLAUDE.md`), not a schema recompile, but the same "can't retune without a release" cost. `RateLimitConfig { burst, refill_per_second }` (`crates/cratestack-axum/src/ratelimit/config.rs:6`) and `IdempotencyLayer::new(store, ttl)` (`crates/cratestack-axum/src/idempotency/layer.rs`) are both constructed **by the consumer, at their own app's startup**, and applied with `.layer(...)` on the router *cratestack generated*.

**Pattern C (found in review, missed by the earlier draft) — dispatch-side enforcement for anything a `tower::Layer` structurally cannot see.** `docs/design/rpc-transport.md` §4's cross-binding table explicitly lists "Per-op rate limit" as `layered route` for HTTP unary/stream but `dispatch-side` for HTTP batch/WS — precisely because a `tower::Layer` only ever sees the raw HTTP request/response, never the N decoded frames inside a batch body. This is strong, on-point precedent for Decision 1 (the frame cap has to live inside `build_batch_block()`, not as a layer) that the earlier draft's recommendation matched by instinct but didn't cite.

**Important nuance on Pattern B the earlier draft missed:** `crates/cratestack-axum/src/idempotency/mod.rs`'s module doc says: "In Phase 1 the layer is opt-in at the consumer's router. A follow-up will wire it into macro-generated routers by default, gated by a `@no_idempotency` opt-out attribute **already recognised by the parser**" (confirmed: `crates/cratestack-parser/src/tests_procedures.rs:157-173` parses `@no_idempotency` today). Two consequences: (a) Pattern B is not a permanent "always opt-in" philosophy — the documented roadmap explicitly plans a default-on, schema-flag-gated version of this exact middleware, so citing "IdempotencyLayer is opt-in" as evidence that body limits must also stay opt-in is not the settled precedent the earlier draft implied. (b) More importantly for Decision 2: since IdempotencyLayer is *opt-in-only today*, there is **no existing case in this codebase** of "a consumer re-layers `IdempotencyLayer`/`.layer(...)` to override a default cratestack already applied." The earlier draft's claim that its override mechanism "mirrors the already-documented IdempotencyLayer post-hoc-layering pattern" cites a pattern that doesn't actually exist yet, on top of being mechanically broken for `DefaultBodyLimit` specifically (below).

## Decision 2 — request body limit default + override

**The earlier draft's Option B recommendation is withdrawn — its override mechanism is empirically broken, not just risky.**

I reproduced cratestack's exact layering shape in a standalone axum 0.8.9 program (the version this repo's `Cargo.lock` actually pins) and ran it:

```
cratestack_router = Router::new().route(...).layer(DefaultBodyLimit::max(2 MiB))   // simulates router()'s build()
consumer_router   = cratestack_router.layer(DefaultBodyLimit::max(10 MiB))          // simulates the proposed override
```

Sending a 5 MiB body (over cratestack's 2 MiB, under the consumer's claimed 10 MiB override) through `consumer_router`:

```
status: 413 Payload Too Large   // should have been 200 if the override worked
```

Also tested: `.layer(DefaultBodyLimit::disable())` on top → still `413`. Tightening the same way (`.layer(DefaultBodyLimit::max(1024))` on top of the 2 MiB baked-in limit, sending 2000 bytes) → still `200 OK`, i.e. the tightened limit was silently ignored too. A control case with no inner cratestack layer confirms the mechanism works fine in isolation — the failure only appears once there's a pre-existing `DefaultBodyLimit` layer to fight.

**Why:** `DefaultBodyLimitService::call()` (`axum-core-0.5.6/src/extract/default_body_limit.rs`) does `req.extensions_mut().insert(self.kind)` **unconditionally, every time it runs** — no "only if not already set" check. axum's own documented layering model (`axum-0.8.9/src/docs/routing/layer.md`, "Ordering" section: "middleware being executed from bottom to top") means the layer added *last* (the consumer's, in the proposed design) runs **first**, and the layer added *earliest* (cratestack's own, baked in before the router is ever returned) runs **last**, immediately before the extractor reads the extension. So whichever `DefaultBodyLimit` sits closest to the handler always wins — and that's structurally always cratestack's own, because a consumer can only ever wrap *around* a Router they've already received, never insert something *between* cratestack's layer and the handler. This is not specific to `DefaultBodyLimit`'s numbers — the same "innermost restriction wins, not outermost" composition applies to any layer that restricts (rather than merely observes) a request, which is why "most recently applied layer wins" — true for something like `Extension` state — does not generalize to size/rate-limiting layers the way the earlier draft assumed.

| Option | Sketch | Pros | Cons | Breaking? |
|---|---|---|---|---|
| **A. Do nothing in code; document the existing axum default** | No codegen change. The override advice given is actually correct, unlike B's. | Doesn't satisfy AC #2's literal text ("Generated routers layer a default body limit") — the router still doesn't *layer* anything itself. | No. |
| **B. Layer `DefaultBodyLimit::max(2 MiB)` inside `router()`/`rpc_router()`, consumer overrides by re-layering** *(as originally proposed)* | — | Names an existing default. | **Broken as specified** — see empirical test above. The override this option's entire pitch rests on does not exist. | No, but ships a documented capability ("overridable by the consumer") that doesn't work. |
| **C. Pick a cratestack-specific default different from axum's 2 MiB, e.g. env-var-driven** | Same as B but with a new number and/or startup env-var plumbing. | — | The earlier draft dismissed this by conflating "picking a different *number*" with "adding *configurability*" — those are separable. An env-var/constructor-driven value **whose default is still 2 MiB** keeps B's "provably a no-op default" property while actually fixing the override (see D). Dismissing C outright threw out its useful half along with its risky half. | Depends on shape chosen. |
| **D. (new) Thread the limit as a real parameter into `router()`/`rpc_router()`, defaulting to `DEFAULT_BODY_LIMIT_BYTES = 2 MiB`** | `router()`/`rpc_router()` take an explicit `body_limit_bytes: usize` (or a builder method defaulting to the constant). Exactly one `DefaultBodyLimit` layer is ever constructed, with the caller's value baked in once — no stacking, no overwrite race. | Actually satisfies AC #2's literal text, verified by construction. Same default (2 MiB) as today, so still a no-op change for anyone who doesn't touch the new parameter. Real, mechanical, pre-1.0-cheap churn — not a design risk. | Yes — but see Reviewer notes on why this is the right kind of breaking change for this repo's stage. |

**Recommendation: Option D.** Option B's pitch was "provably a no-op behavior change... consciously overridable" — the first half is true, the second is false, and AC #2 explicitly requires the second half ("overridable by the consumer"). Shipping code that claims an override capability it doesn't have is worse than shipping nothing (Option A) — a consumer who trusts the docs and tries to raise the limit for a legitimate large-payload endpoint will get silent, confusing 413s with no signal that their override was ignored. If the maintainer wants zero signature churn instead of Option D, the honest choice is Option A plus renegotiating AC #2's wording with the issue author, not Option B.

**Supporting number check (unchanged from earlier draft, still holds):** `BATCH_MAX_ITEMS` (1000 frames) fits comfortably inside a 2 MiB request at any realistic average frame size, so 2 MiB remains a sound default even once Decision 1 ships — this wasn't invalidated by the override finding, only the mechanism for changing it away from the default was.

## Decision 3 — bound for the four `to_bytes(usize::MAX)` response sites

Sites confirmed present at the cited lines: `crates/cratestack-axum/src/rpc/batch.rs:36`, `error_encode.rs:55`, `grpc_bridge.rs:50`, `codec_helpers.rs:59`. Verified detail the earlier draft glossed over: `error_encode.rs`'s `convert_handler_error_response` early-returns unbuffered for any 2xx response (`if response.status().is_success() { return response; }`) — its `to_bytes` call only ever runs on *error* bodies, which are always small, synthesized-shape payloads. `codec_helpers.rs:59`'s site buffers a *re-encoded request input* value (used by `batch.rs`'s per-frame loop to round-trip a frame's `input` field through the codec), not literally "a dispatcher response" the way the other three are — same treatment (bound it) is still correct, just a small precision note for the doc comment, not a defect.

None of the four sites face an untrusted upstream/proxied body — all buffer a `Response` produced in-process — so this bound is a safety valve against a pathological in-process response, not a network-trust boundary. Same two options as the earlier draft, still real (this part of the earlier draft holds up):

| Option | Sketch | Pros | Cons | Breaking? |
|---|---|---|---|---|
| **A. Reuse `DEFAULT_BODY_LIMIT_BYTES`** | Replace all four `usize::MAX` with the Decision-2 constant. | One number, simplest to document. | A `create`/`update` response echoing the request payload plus server-added columns could legitimately exceed a request right at the ceiling, failing on the response side with an opaque `Internal` error. | No — strictly tightens an unbounded path, but see the edge case. |
| **B. Separate, larger constant — documented multiplier (4×, proposing 8 MiB)** | New `pub const MAX_RESPONSE_REBUFFER_BYTES: usize = 4 * DEFAULT_BODY_LIMIT_BYTES;`, used at all four sites. | Headroom for A's edge case; still a hard, testable ceiling. | 4× is a starting point, not measured. | No — same reasoning as A. |

**Recommendation: Option B, unchanged**, with two additions the earlier draft didn't make: (1) the multiplier isn't purely a guess — `MAX_LIST_LIMIT` (1000 rows) already bounds how large a `list` response's item array can be, and `BATCH_MAX_ITEMS`-capped batch responses (once Decision 1 ships) are similarly row-count-bounded, so 8 MiB has an actual ceiling-on-the-ceiling to point to, not just "4× felt right." (2) **Caveat to add to the doc, not resolve here:** `docs/design/rpc-transport.md` documents genuinely-incremental, unbounded-size streaming delivery for `@stream` ops (#282/#283, `Body::from_stream`, no `Vec<u8>` ever materialized server-side) as a deliberately-built property. `batch.rs`'s `response_to_frame` buffers *every* frame's response unconditionally regardless of whether that frame's op is `@stream`-shaped — §3.2 of the RPC transport doc doesn't say whether `@stream` ops can even be dispatched through `/rpc/batch` at all. If they can, this buffering already happens today (pre-existing, not introduced by this change) — applying `MAX_RESPONSE_REBUFFER_BYTES` there doesn't make it worse, but the doc note for this change should say explicitly that it does *not* newly make batch `@stream`-safe, so a future reader doesn't assume it does.

## Implementation sketch (once the above is confirmed)

1. `crates/cratestack-core/src/`: **new file** `limits.rs` (not appended to `page.rs` or `batch.rs` — those two already live in different files scoped to their own concern, so a cross-cutting body/response-size constant belongs in its own module, consistent with the repo's one-file-per-concern layout). Define `pub const DEFAULT_BODY_LIMIT_BYTES: usize` (used as Decision 2's *default*, not the only value once Option D threads it as a parameter) and `pub const MAX_RESPONSE_REBUFFER_BYTES: usize = 4 * DEFAULT_BODY_LIMIT_BYTES`.
2. `crates/cratestack-macros/src/include/server/rpc_module/batch.rs`: frame-count check against `BATCH_MAX_ITEMS` before the per-frame loop in `build_batch_block()`, erroring through `rpc_dispatch_error` with a `CoolError::Validation` message mirroring `validate.rs`'s wording. (86 lines today — comfortably under the 200-line ceiling after this addition.)
3. `crates/cratestack-macros/src/include/server/axum_module/router_fn.rs` and `.../rpc_module.rs`: add a `body_limit_bytes: usize` parameter to `router()` (both `ServerDb` arms) and `rpc_router()`, defaulting call sites that don't care to `DEFAULT_BODY_LIMIT_BYTES`; `.layer(DefaultBodyLimit::max(body_limit_bytes))` at the end of each. Leave a comment in each file cross-referencing the other — this exact two-codegen-path split (REST vs RPC not sharing a merge point) is what let the batch cap go missing for RPC in the first place.
4. `crates/cratestack-axum/src/rpc/{batch,error_encode,grpc_bridge,codec_helpers}.rs`: replace `usize::MAX` with `MAX_RESPONSE_REBUFFER_BYTES`; the existing `Err(error) =>` arm at each site already synthesizes a `CoolError::Internal`/error-frame response for any buffering failure, so a `LengthLimitError` on overflow needs no new match arm — the existing generic error path already covers it (verified by reading all four call sites; each already has this arm).
5. Docs: `docs/design/rpc-transport.md` §3.2 gets the frame-cap note; a new short design doc (or a section of the same file) documents `DEFAULT_BODY_LIMIT_BYTES`, `MAX_RESPONSE_REBUFFER_BYTES`, the *actual* override mechanism (a constructor parameter, not re-layering), and explicitly flags that `DefaultBodyLimit` re-layering does **not** work as an override for a value cratestack itself already layered — worth stating plainly so a future contributor doesn't reintroduce Option B's mistake.

## Test strategy

- **Frame cap:** a *new* `db = None` + `transport rpc` procedures-only fixture (none exists today — see Decision 1) posting `BATCH_MAX_ITEMS + 1` minimal frames to `/rpc/batch`, asserting rejection before any frame's `authenticate()` runs (spy `AuthProvider`). No `CRATESTACK_TEST_DATABASE_URL` required once that fixture exists.
- **Body limit:** POST an over-limit body to a `db = None` procedure-backed REST/RPC route (no PG needed, since rejection happens at the `Bytes` extractor before any handler/DB code runs) and assert `413`; a second test constructing the router with a different `body_limit_bytes` argument and asserting the new ceiling actually takes effect — this is the test that would have caught Option B's broken override before it shipped, so it should be written as a real assertion (send a body between the old and new limit, expect success), not just "still rejects something huge."
- **Response rebuffer bound:** a handler/procedure fixture returning a payload over `MAX_RESPONSE_REBUFFER_BYTES`, asserting the four call sites degrade to a clean error rather than unbounded allocation — closest to `cratestack-axum`'s existing `crates/cratestack-axum/src/rpc/tests_*.rs` modules, `cargo test -p cratestack-axum` scope.
- No PG-backed (`just test-pg`) coverage required for any of the three, consistent with the earlier draft.

## Reviewer notes

- **Headline correction (Decision 2):** the earlier draft's recommended Option B claimed a working override mechanism ("re-apply `.layer(DefaultBodyLimit::max(n))` on the returned `Router`"). I verified this empirically against axum 0.8.9 (this repo's pinned version) and it does not work in *either* direction — raising, disabling, and even tightening via the same mechanism all silently fail, because `DefaultBodyLimitService` unconditionally overwrites a request extension on every layer invocation and axum's own documented layer-execution order means cratestack's own (earliest-applied) layer always runs last, closest to the handler. Reversed the recommendation to a new Option D (thread the limit as a real constructor parameter) rather than a passively-layered default. This is the one change in this revision that alters the bottom-line recommendation; everything else is grounding, precision, or scope notes on decisions that already held up.
- Added Pattern C (`docs/design/rpc-transport.md` §4's cross-binding table: rate limiting is "layered route" for unary but "dispatch-side" for batch) as prior art the earlier draft's Decision 1 reasoning matched by instinct but never cited — makes Decision 1's recommendation better-grounded, no change to the recommendation itself.
