# Function-shaped `@default(...)` values

Status: implemented by the PR that closes cratestack#1209.

## The problem

A `@default(fn())` reaches a migration's `DEFAULT` clause. Before this change, cratestack did no checking at all:

- `cratestack check` accepted any call;
- `migrate diff` wrote the call verbatim into both the Postgres and SQLite trees;
- the database refused the migration when it was applied.

Four failures came out of that:

- **Unknown functions.** `uuid()` and `cuid()`, the Prisma spellings, do not exist in Postgres: `function uuid() does not exist`.
- **SQLite syntax.** SQLite accepts a function call in `DEFAULT` only inside parentheses, so *every* function default failed there, `now()` included: `near "(": syntax error`.
- **Auth defaults in DDL.** `@default(auth().id)` was emitted as `DEFAULT auth().id`.
- **Embedded runtime.** The embedded tables (`cratestack_rusqlite::ddl::create_table_sql`) carry no `DEFAULT` clauses at all. Any `@default` column was therefore written as NULL, and the create failed when it decoded the returned row.

cratestack#1167 closed the `autoincrement()` spelling the same way and left this as its follow-up.

## Decisions

### 1. cratestack defines `now()`, `uuid()` and `cuid()`

They are generated **in Rust, on create**, on both runtimes:

- **Mechanism:** `GeneratedDefault` in the model descriptor, filled by `ModelDescriptor::fill_generated_defaults`.
- **Server runtime:** `cratestack-sqlx`'s four create paths.
- **Embedded runtime:** `cratestack-rusqlite`'s create, batch create, upsert and batch upsert.

The value is therefore the same on every backend and never depends on a database default.

| Function | Field types | Value | Postgres `DEFAULT` | SQLite `DEFAULT` |
| --- | --- | --- | --- | --- |
| `now()` | `DateTime` | current UTC time | `now()` | `(strftime('%Y-%m-%dT%H:%M:%fZ', 'now'))` |
| `uuid()` | `Uuid`, `String` | random v4 UUID | `gen_random_uuid()` (core since PG 13) | a v4 expression over `randomblob` |
| `cuid()` | `Cuid`, `String` | 24-char cuid2-shaped id | none | none |

The database defaults are still emitted, for writes that bypass cratestack (`psql`, triggers, other services). The SQLite expressions produce exactly what the embedded runtime binds and decodes: RFC 3339 UTC text, and a hyphenated lowercase UUID. `cuid()` has no database equivalent, so a writer outside cratestack must supply it.

`cuid()` is generated by `cratestack_core::cuid::new_cuid` from a CSPRNG, in cuid2's default shape (`[a-z][0-9a-z]{23}`). It does not run the cuid2 algorithm's hash. The `cuid2` crate pulls in `getrandom` 0.3, which does not build for `wasm32-unknown-unknown` without extra configuration, and the embedded runtime runs there. The randomness comes from `uuid`'s v4 generator, which every runtime already depends on.

### 2. Functions the database provides are registered

```cstack
datasource db {
  provider  = "postgresql"
  url       = env("DATABASE_URL")
  functions = ["next_ticket_ref", "public.other_fn"]
}
```

- **At `check`:** a `@default(fn(...))` must name a cratestack builtin or a registered function. Anything else is refused, with a hint where one helps (`gen_random_uuid()` → `uuid()`).
- **What registering means:** it is an assertion, like `dbgenerated()`. cratestack writes the call verbatim (parenthesised on SQLite), and the database refuses the migration if the function does not exist. `cratestack-pg/tests/generated_defaults.rs` pins both halves against a real Postgres.
- **Names:** a registered name may be schema-qualified. cratestack's own names (`now`, `uuid`, `cuid`, `dbgenerated`, `autoincrement`, `auth`) cannot be registered.
- **Postgres built-ins:** `gen_random_uuid()` and `clock_timestamp()` need registering too, rather than being allowed implicitly. That keeps one rule, and `uuid()`/`now()` cover the common cases on every backend.

### 3. `cs_cuid()` fixtures move to `cuid()`

Twenty-three client-codegen fixtures used `@default(cs_cuid())`, which is defined nowhere. They now use the builtin. Codegen is unchanged, since any `@default` already removed the field from the Create input.

## Parser rules

All of these go through `cratestack_core::schema::default_functions::classify_default`. The migration emitter classifies with the same function, so the two cannot disagree.

- **Built-ins:** exact spelling, no argument, the whole expression, on a field of a type the value fits. `UUID()`, `uuid(4)`, `now() + 1` and `uuid()` on an `Int` are refused. So is a bare `now` on a `DateTime`, which would be emitted as the literal `DEFAULT now`.
- **Unregistered functions:** refused.
- **`auth()` in a database expression:** refused (`lower(auth().email)`). An auth default is exactly `@default(auth().field)`.

## Migrations and snapshots

`ColumnDefault` gains `Generated(GeneratedDefault)`, rendered per dialect by `emit::{postgres,sqlite}::defaults`.

**Old snapshots are normalised when read:**

- `Function("now()" | "uuid()" | "cuid()")`, in any spelling, reads as `Generated`. An old `Function("uuid()")` therefore never reverses into `SET DEFAULT uuid()`.
- `Literal("auth().field")` reads as no default.

**Introspection:** Postgres's `now()` and `gen_random_uuid()` read back as `Generated(Now)` and `Generated(Uuid)`.

**Adding a column:**

- On Postgres, a `cuid()` column backfills nothing. A required one is therefore blocking, like a column with no default.
- On SQLite, any expression default fails with "Cannot add a column with non-constant default" once the table has rows. The SQLite emitter writes a note there, as it already does for the other `ALTER` forms SQLite lacks.

## Known gaps, not addressed here

- **Embedded runtime:** it still applies no `@default(auth().field)` and no `dbgenerated()` default, because `create_table_sql` has no `DEFAULT` clauses. Such a column is written as NULL.
- **Other function defaults through cratestack:** registered functions and `dbgenerated()` are filled only by the database.
